# 舊資料相容與帳號同步

## 不需要搬移帳號資料

沿用原本 Firebase 專案、Google 登入與 `users/{uid}` 路徑，不更換 UID、不重建帳號、不批次改寫正式訂單。

`normalizeWorkspace` 保留原始檔期、商品與訂單陣列。分類的舊 ID、選項名稱、規格文字、訂單建立日期、單價與總額保持原樣。新增的 `currency`、`costRate`、`archived` 是選用欄位：舊檔期沒有幣別時沿用既有日圓假設，沒有成本匯率時沿用舊全域值。新檔期需自行設定幣別與換算率。

歷史訂單保存加入商品當時的名稱、規格、原價、成交單價與小計。修改商品或售價換算率只影響之後加入的商品，不重算歷史訂單。已有商品或訂單的檔期禁止直接改變幣別，避免錯誤解讀原價。

## 帳號與同步界線

1. 每個登入帳號建立獨立的同步實例與 `dg_workspace_v2:user:<uid>` 快取；訪客使用另一個 key。
2. 讀取第一份權威伺服器快照前不可編輯，也不會上傳本機資料或預設工作區。
3. 每次雲端寫入使用交易讀取目前版本，與客戶端的基準完整比對；不以本機時鐘決定誰覆蓋誰。
4. Firestore Rules 要求使用者的 UID 符合文件路徑，且寫入具有 schema、不同 revision 和完整的頂層資料形狀。
5. 帳號切換停止舊實例與待執行寫入。舊實例遲到的回應不會進入新帳號畫面。
6. 衝突保留本機修改、停止寫入，提供下載備份與載入雲端版本。
7. 訂單、商品與檔期的編輯視窗會比較開啟時的原始內容；若已被另一台裝置更新，拒絕覆蓋。

訂單建立草稿另以 `dg_order_draft_v1:user:<uid>:<batchId>` 保存；它不會加入雲端正式訂單。帳號與檔期切換後可取回自己的草稿。草稿中的商品已被移除或封存時，送出前會提示使用者修正。

## 封存與缺少設定

- 有商品或訂單的檔期使用封存，可查詢、編輯既有訂單、更新狀態與匯出，恢復後才能建立新訂單。
- 被訂單引用的商品使用封存；歷史成交資料仍以訂單快照為準。
- 使用中的分類先選擇移轉目標，再一次更新商品與分類。
- 沒有對應檔期設定的歷史資料會顯示為「未歸檔歷史資料」。這個入口只在畫面計算，不會自動加入雲端檔期；必須核對幣別與匯率後才可手動修復，仍使用原本的檔期編號。

## 匯入與快取恢復

JSON 匯入會先檢查編號、分類／選項格式、價格、整數數量、狀態、日期與品項／訂單金額的一致性，顯示目的帳號與資料筆數，確認並完成本機備份後才取代工作區。檢查失敗不更動目前資料。雲端歷史讀取不套用這份較嚴格的匯入檢查，避免新版驗證封鎖原有訂單。

無法解析的快取不會被當成空資料覆寫；接受伺服器資料前先保存原始內容。備份或儲存空間不足時停止取代及同步，提供原始快取下載。訂單編輯衝突時，可下載仍在視窗中的編輯草稿。

本機儲存僅是工作副本，清除瀏覽器資料會清除未同步的草稿及備份。實際帳號的已同步資料保留在雲端；需要轉移本機草稿時，先下載備份。
